# 日常提醒

老人用一句话把一件事交给可可，到点由确定性规则叫他，并把「他怎么回应的」如实记下来。

本文是提醒能力的完整设计，覆盖数据模型、调度、呈现、反馈与家庭升级。

与其他文档的关系：

- [`doc/需求.md`](需求.md) 第 7–9 章定义了 F02 的产品边界，本文与之一致；
- [`doc/可可_Agent总体设计.md`](可可_Agent总体设计.md) 第 5.1–5.3、7.4 节定义了 Agent 侧规则，本文是它的工程落地；
- 与总体设计的偏差只有一处：总体设计要求 `version` 字段做并发保护，本文改用单向 `revision` 快照，理由见「计划变更」一节。

## 心智模型

提醒由两个对象组成，任何时候都不要把它们混在一起：

| 对象 | 回答的问题 | 生命周期 |
| --- | --- | --- |
| **计划** `reminders` | 以后要在什么时间叫他做什么 | 长期存在，可改可停可删 |
| **一次到点** `reminder_occurrences` | 这一次叫了没有，他怎么回应的 | 每次触发新建一条，独立收尾 |

一次到点是**唯一真相**。系统本地通知、App 内浮层、语音反馈三条渠道携带同一个 `occurrence_id`，任一渠道先写入，其余渠道自动收起。跨渠道去重不需要额外机制。

大模型不判断时间。时间、重复、状态推进、幂等与升级全部由确定性规则执行；模型只负责听懂、追问、复述和播报。

## 数据模型

### 计划：`reminders`

```text
id
user_id
title
schedule_type          ONCE | DAILY
schedule_time          本地时刻，按 local_timezone 解释
status                 ACTIVE | PAUSED | DONE | DELETED | PENDING_CONFIRM | REJECTED
created_source         PARENT | VOICE | CHILD
suggested_by_user_id   子女建议时记录建议人
next_trigger_at        UTC，调度器扫描依据；PENDING_CONFIRM 时为空
timing_mode            EXACT | FLEXIBLE          （新增）
allowed_delay_minutes  仅 FLEXIBLE 使用，默认 15  （新增）
escalation_policy      NONE | FAMILY_AFTER_TWO_UNANSWERED（新增）
revision               计划版本号，改一次加一    （新增）
```

`next_trigger_at` 只表示「下一次计划触发」。**任何临时延后都不得改写它**。

### 一次到点：`reminder_occurrences`

状态拆成两个正交字段，这是整套设计的核心：

```text
id
reminder_id
due_at
delivery_state         PENDING | NOTIFIED_1 | NOTIFIED_2 | CLOSED   调度器拥有
response_status        NONE | COMPLETED_SELF_REPORTED |            用户拥有
                       SKIPPED_SELF_REPORTED | SNOOZED | UNANSWERED
reminder_revision      创建时冻结，用于让旧计划的触发失效
title_snapshot         冻结标题，改名后历史仍可读
snooze_until           延后落在这里
attempt_count          同一次到点提示了几遍
response_source        VOICE | BUTTON | NONE
first_notified_at / second_notified_at / responded_at / escalated_at
```

`delivery_state` 只回答「系统提示到第几次」，`response_status` 只回答「老人怎么回应」。调度器不写第二个字段，唯一例外是 App 关闭场景下回填 `UNANSWERED`。

**为什么必须拆开。** 合并成一个字段时，`DONE` 会同时表示「说做过了」和「点了延后」，于是完成、跳过、无回应三种语义无法区分，家庭升级也就无法判断该不该发。拆开之后，这些规则都变成对两个字段的简单读取。

### 计划变更

改计划时 `revision` 加一，并重算 `next_trigger_at`。到点创建 occurrence 时冻结当时的 `revision`；提示前比对，不一致直接 `CLOSED`。

这样「暂停、删除或旧版本提醒不会触发」自然成立，不需要乐观锁——符合 [`AGENTS.md`](../AGENTS.md) 对 MVP 基础设施的克制要求。

## 创建与确认

三条入口，共用同一套写入规则：

| 入口 | 确认方式 | 落库状态 | 是否调度 |
| --- | --- | --- | --- |
| 父母提醒页 | 表单提交即视为已确认 | `ACTIVE` | 立即排 `next_trigger_at` |
| 语音 `create_reminder` | 先 `user_confirmed=false` 出确认大卡，点卡或口头说「好」后再 `true` | `ACTIVE` / `VOICE` | 确认后才写入 |
| 子女建议 | 父母在首页建议卡 accept / reject | 先 `PENDING_CONFIRM` | 确认前 `next_trigger_at` 为空 |

规则：

- 创建、修改、暂停、删除提醒都是 **A2**：复述事项、时间、重复和时间等级，确认一次，不逐字段确认；
- 缺信息时一次只追问一个关键字段；
- 子女只能建议，不能直接创建、修改或删除父母的提醒；
- 所有写操作带 `idempotency_key`，重复语音、重复点击、网络重试不得产生第二条；
- 未拿到写入成功回执，不得说「设好了」；成功反馈必须包含下一次触发时间。

### 时间规则

支持明确钟点、单次、每天。未说明重复时默认仅一次。

「饭后」「睡前」「运动完」系统无法可靠感知，不作为触发条件，只追问一个大致钟点。复杂轮班、阴历、不规则间隔本期不支持，不能可靠表达时说明限制，**不自行近似**。

### 时间等级

`timing_mode` 由可可按已确认规则推断，不要求老人每次选择：明确钟点、用药、复诊默认 `EXACT`；喝水、活动、休息等习惯默认 `FLEXIBLE`。无法判断且延迟会影响结果时，只追问一句「要我准点提醒，还是方便的时候提醒？」。

最终确认语句里用「准时」或「方便时」让老人感知，不暴露枚举名。

## 触发与推进

调度器每 `reminder_scan_interval_seconds`（默认 30 秒）扫一轮，分两步：建新 occurrence，推进未收尾的 occurrence。状态推进写成纯函数，便于单测；多实例用 `SKIP LOCKED` 避免重复触发。

```text
到点
  → 建 occurrence，冻结 revision 与标题
  → DAILY 同时预排下一次 next_trigger_at
  → 校验 revision 一致（不一致直接 CLOSED）
  → delivery_state = NOTIFIED_1，写通知，客户端起浮层
  → 浮层内 10 秒无回应 → 可可提示一句 → 再 10 秒
  → 仍无回应：客户端上报 UNANSWERED，关浮层，恢复原任务
  → 30 分钟后 delivery_state = NOTIFIED_2，attempt_count = 2，再次显著提示
  → 仍为 UNANSWERED 且升级策略已授权 → 通知主要子女一次 → CLOSED
```

延后走另一条支路：`response_status = SNOOZED` 并写 `snooze_until`，`delivery_state` 退回 `PENDING`。调度器扫到已过期的 `snooze_until` 重新提示，`attempt_count` 累加。**计划表全程不动**，一次性提醒也不需要把状态改回 `ACTIVE`。

两次提示属于同一个 `occurrence_id`，靠 `attempt_count` 区分，不创建重复事项。30 分钟是可配置的重试间隔，**不代表任何医疗安全间隔**。

## 呈现

`EXACT` 与 `FLEXIBLE` 只决定在持续对话中**什么时候介入**，不决定提醒强弱。一旦正式提示，两者都使用显著的声音、震动和大字视觉，不得把弹性提醒降级成容易忽略的普通通知。

因此服务端对两者的投递逻辑完全一致，差异只发生在客户端。**服务端不需要感知会话状态。**

| 当前状态 | `EXACT` | `FLEXIBLE` |
| --- | --- | --- |
| App 关闭 | 系统级有声提醒、震动、锁屏卡片 | 同左 |
| App 前台待机 | 可可主动开口并展示浮层 | 同左 |
| 可可正在说话 | 停止当前播报，立即提示 | 等本轮说完或自然停顿 |
| 老人正在说话 | 立即响铃、震动、展示浮层；当前一句结束后再播报 | 等自然停顿；超过 `allowed_delay_minutes` 先发信号，当前一句结束后播报 |
| 可逆任务进行中 | 暂停当前事项，处理后恢复 | 在允许窗口内等停顿 |
| 不可安全中止的动作中 | 先发提示信号，动作返回明确结果后再播报 | 等动作返回结果后提示 |

### App 内浮层

提醒**不跳转新页面**，在当前页面上盖一层大尺寸中断式浮层：

- 背景保留并弱化，让老人知道原来的事没消失；
- 浮层出现后背景不可操作，一屏只处理这一件事；
- 大字、高对比、整行大触控区，不做成小尺寸系统弹窗；
- 可可形象保持可见并切换为主动提醒状态，同时说一句简短提醒；
- **不允许点击浮层外区域或轻扫误关闭**；
- 处理完成后关闭浮层，直接露出原页面，按上下文恢复对话或工具。

浮层需提升到 router 层的全局宿主，任意页面都能盖上，不能只挂在父母首页。

App 关闭时点击系统通知进入，落到同一浮层；没有可恢复的原页面时以首页作为弱化背景。

### 本地通知

创建、修改、反馈后**立即**重排未来若干次本地定时通知，不能等退到后台才排——否则用户直接杀进程就收不到。

锁屏文案只显示「可可有一条提醒」，**不显示药名、疾病或具体健康事项**。具体事项进 App 才展示。

payload 携带 `occurrence_id`；前台读到该次已有响应即撤销对应本地通知，保证系统通知与 App 内呈现不重复。

## 反馈

浮层出现时可可用开放式问题邀请老人回答，而不是让他在两个按钮里选：

> 到八点了，该吃药了。现在怎么样？

浮层只放两个最高频快捷动作：**完成了**、**晚点提醒**。语音可以表达任何其他情况。

语音已启动时状态条显示「我在听，直接告诉我」；麦克风未启动时显示「点一下，告诉可可」，**单击一次即开始收音，不要求长按**。

| 老人表达 | 记为 | 处理 |
| --- | --- | --- |
| 「完成了」或点完成 | `COMPLETED_SELF_REPORTED` | 只记自述，**不得表述为系统已验证服药或执行** |
| 「晚点提醒」或点晚点 | `SNOOZED` | 按钮固定再延 30 分钟；语音说出具体时间时以老人给的时间为准 |
| 「今天不做了」 | `SKIPPED_SELF_REPORTED` | 仅跳过本次，重复计划继续有效 |
| 「以后别提醒了」 | 不记为跳过 | 转入暂停或删除流程并确认 |
| 身体不适、求助、高风险表达 | 安全流程 | 先关怀并判断风险，再记录反馈 |
| 没有任何回应 | `UNANSWERED` | **不得推断为未完成**，按重试规则处理 |

成功反馈示例：「记下了，你说已经完成。」

### 无回应由谁判定

| 场景 | 谁写 `UNANSWERED` | 理由 |
| --- | --- | --- |
| App 前台，浮层展示中 | 客户端，10 + 10 秒后上报 | 只有客户端知道浮层是否真被看见 |
| App 关闭，只发了系统通知 | 服务端，二次提示时回填 | 没有交互信号，只能记为未回应 |

## 家庭升级

| 提醒类型 | 默认策略 |
| --- | --- |
| 饮水、活动、吃饭等生活习惯 | `NONE`，不因未回应通知子女 |
| 用药、复诊、检查等重要健康提醒 | 服务端按标题关键词推断默认 `FAMILY_AFTER_TWO_UNANSWERED`，并在确认大卡明示「没回应时会告诉家人」 |
| 子女建议的提醒 | 老人确认时一并确认是否允许升级 |
| 老人明确求助或高风险表达 | 不等两次，立即进入安全流程 |

连续两次无回应且策略已授权时，只向主要子女发**一次**最小化通知：

> 今晚 8 点的健康提醒连续两次没有收到回应。请联系奶奶确认情况。

通知只描述「没有收到回应」，不推测没看到手机、忘记执行或身体异常。子女端提供电话或微信入口，但未回应本身不标记为紧急事件。

## 接口

```text
POST   /v1/reminders                          创建（带 idempotency_key）
GET    /v1/reminders                          父母的有效提醒列表
PATCH  /v1/reminders/{id}                     改标题 / 时间 / ACTIVE|PAUSED，revision +1
DELETE /v1/reminders/{id}                     标记删除，撤销后续触发

POST   /v1/reminders/suggestions              子女建议，落 PENDING_CONFIRM
GET    /v1/reminders/suggestions              子女查看自己提过的建议
POST   /v1/reminders/{id}/accept              父母确认 → ACTIVE 并开始调度
POST   /v1/reminders/{id}/reject              父母拒绝 → REJECTED，通知子女

POST   /v1/reminders/occurrences/{id}/response
       body: { status, snooze_until?, source, idempotency_key }
```

反馈收敛为**一个**端点，替代原先的 `/confirm` 与 `/delay`。URL 里不重复 `occurrence_id` 的父级 `reminder_id`，归属由服务端校验。

幂等：同一 occurrence 已是终态时直接返回当前状态，不报错。

## 语音工具

| 工具 | 等级 | 说明 |
| --- | --- | --- |
| `create_reminder` | A2 | 两段式：先 `user_confirmed=false` 出大卡，确认后 `true` |
| `respond_to_reminder` | A0 | 覆盖完成 / 跳过 / 延后；延后必须带老人给出的时间 |
| `update_reminder` | A2 | 多条匹配时只追问一个区分字段；失败保留旧计划 |
| `pause_reminder` / `resume_reminder` | A2 | 暂停即清空 `next_trigger_at`；恢复时重算 |
| `delete_reminder` | A2 | 标记删除，不物理清除既有反馈记录 |
| `list_reminders` | A0 | 查询当前有效提醒 |

系统提示词须包含：老人说「以后别提醒了」要走暂停或删除确认，不能记成跳过一次。

## 不可破坏的规则

- **确认后才写入**：创建、修改、暂停、删除提醒必须经老人明确确认；子女建议在老人确认前不注册、不触发。
- **完成只是自述**：`COMPLETED_SELF_REPORTED` 不得在任何文案、统计或通知中表述为系统已验证。
- **无回应不等于未完成**：不得推断成没吃药、拒绝执行或身体异常。
- **不产生医疗计划**：只记录用户、家人或专业人员已给出的安排，不判断药量、服药间隔或医疗必要性。「一天三次」但没给钟点时，请老人按医嘱或药盒提供时间，**不自行平均分配**。
- **锁屏不暴露健康隐私**：系统通知只显示通用文案。
- **不重复响**：系统通知与 App 内呈现共享 `occurrence_id` 并去重。
- **弹性不等于微弱**：`FLEXIBLE` 一旦进入提示阶段，显著程度与 `EXACT` 相同。

## 与当前实现的差距

已经落地：三条创建入口、`PENDING_CONFIRM` 建议流、occurrence 双字段、延后只动 occurrence、统一 `POST /v1/reminders/occurrences/{id}/response`、关键词推断 `escalation_policy`、`revision` 快照、全局到点浮层、创建/确认后立即排本地定时、锁屏通用文案。

仍待阶段三：`timing_mode` 抢占、语音管理工具、10 + 10 秒超时、幂等键。

### 迁移注意

旧状态映射：

```text
WAITING          → PENDING    / NONE
FIRST_REMINDER   → NOTIFIED_1 / NONE
SECOND_REMINDER  → NOTIFIED_2 / NONE
ESCALATED        → CLOSED     / UNANSWERED
DONE             → CLOSED     / COMPLETED_SELF_REPORTED
```

`DONE` 无法区分是确认还是延后，只能一律回填为自述完成。**该批历史数据的完成率统计口径不可靠**，需在迁移说明中标注。
