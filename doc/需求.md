# 可可 Coco MVP 产品需求文档
版本：MVP v1.0  
文档用途：AI 辅助开发 / 产品研发对齐  
目标平台：iOS / Android  
产品形态：同一 App，父母端与子女端两种角色

---

# 1. 产品定义

## 1.1 一句话定义

可可 Coco 是一个面向老人与子女的 AI 家庭陪伴助手。

父母可以像和一个熟悉的人说话一样直接与可可交流；可可负责陪伴、提醒、记录重要信息，并在父母授权或确有必要时，将信息整理后同步给子女。

子女端不承担复杂监控功能，而是帮助子女快速知道：

1. 父母今天整体是否正常；
2. 是否有事情需要自己关注；
3. 是否需要主动联系父母。

原原型的设计原则是“一个 App、两种角色；父母端语音优先，子女端快速理解并行动”。fileciteturn1file4L220-L227

---

# 2. MVP核心目标

MVP只验证三个核心价值。

## 2.1 老人愿不愿意持续和 AI 说话

核心能力：

- 语音对话；
- 连续聊天；
- AI理解老人表达；
- AI记住少量经过确认的重要信息。

重点不是完成多少工具功能，而是让老人形成：

> “有事情或者无聊的时候，可以找可可。”

---

## 2.2 AI能不能真正帮老人处理日常小事

首版只重点验证：

- 创建提醒；
- 主动提醒；
- 老人确认完成；
- 未确认再次提醒；
- 必要时通知子女。

不在 MVP 中做复杂健康管理。

---

## 2.3 AI能不能成为父母与子女之间的沟通桥梁

核心不是同步聊天记录。

而是：

父母自然表达  
→ 可可理解  
→ 可可适当追问  
→ 提炼关键信息  
→ 父母决定是否告诉子女  
→ 子女看到简短摘要  
→ 子女决定是否联系父母。

子女也可以反向向父母“报个平安”。

---

# 3. 用户角色

## ROLE_PARENT

父母 / 老年用户。

设计原则：

- 语音优先；
- 尽量少打字；
- 一屏只处理一件事情；
- 重要操作需要确认；
- AI主动告诉用户下一步；
- 不要求用户理解复杂 App 导航。

---

## ROLE_CHILD

成年子女。

设计原则：

- 信息密度可以高于父母端；
- 打开 App 10 秒内理解家庭状态；
- 结论优先；
- 默认只突出一件真正需要关注的事情；
- 减少无意义通知。

原型对子女首页的目标也是让子女快速判断“家人是否正常、是否需要行动”。fileciteturn1file1L62-L67

---

# 4. MVP功能范围

MVP只实现以下 6 个核心模块。

| ID | 功能 | 优先级 |
|---|---|---|
| F01 | AI语音陪伴 | P0 |
| F02 | 日常提醒 | P0 |
| F03 | 关怀理解与家庭同步 | P0 |
| F04 | 子女今日状态 | P0 |
| F05 | 子女报平安 | P0 |
| F06 | AI基础记忆 | P0 |

除此之外的功能默认不进入第一版。

---

# 5. F01 AI语音陪伴

## 5.1 功能目标

父母打开 App 后，可以直接与可可进行语音交流。

不要求用户提前选择：

- 聊天；
- 创建提醒；
- 说身体情况；
- 找功能。

AI自动判断用户意图。

---

## 5.2 首页

父母端首页保持极简。

页面主要元素：

- 可可角色形象；
- 当前状态；
- 大型语音按钮；
- 一句引导语。

示例：

> 上午好，我在呢，想聊什么？

支持用户直接说：

> 陪我聊会儿。

> 晚上八点提醒我吃药。

> 我今天腿有点酸。

> 我女儿今天怎么没消息。

原型本身也是通过一个统一入口承接普通聊天和任务，而不是要求老人提前选择模式。fileciteturn2file9L503-L509

---

# 6. AI意图识别

每次用户输入后，AI必须先判断意图。

建议使用统一 Intent Schema。

```json
{
  "intent": "CHAT",
  "confidence": 0.96,
  "entities": {},
  "need_confirmation": false
}
```

MVP支持以下 Intent：

```text
CHAT
CREATE_REMINDER
UPDATE_REMINDER
DELETE_REMINDER
REMINDER_CONFIRM_DONE
REMINDER_DELAY
CARE_CONVERSATION
SHARE_TO_CHILD
DO_NOT_SHARE
REPORT_CHILD_STATUS
MEMORY_QUERY
MEMORY_DELETE
UNKNOWN
```

原则：

如果 AI 无法确定用户意图：

不要猜测执行操作。

进入 UNKNOWN：

> “我刚才没听明白，你可以再说一次。”

---

# 7. F02 日常提醒

## 7.1 创建提醒

用户可以通过自然语言创建提醒。

例如：

> 每天晚上八点提醒我吃药。

AI解析：

```json
{
  "title": "吃药",
  "schedule_type": "DAILY",
  "time": "20:00"
}
```

---

## 7.2 创建前确认

涉及未来自动执行的任务，必须确认。

AI：

> “好的，你是想让我每天晚上八点提醒你吃药，对吗？”

用户确认后才能创建。

---

# 8. Reminder 数据模型

```json
{
  "id": "reminder_xxx",
  "user_id": "user_xxx",
  "title": "吃药",
  "schedule_type": "DAILY",
  "schedule_time": "20:00",
  "status": "ACTIVE",
  "created_source": "PARENT",
  "created_at": "",
  "next_trigger_at": ""
}
```

注意：

MVP只记录“提醒内容”。

不保存：

```text
药物剂量
疾病诊断
医疗建议
治疗方案
```

AI不能提供修改药量等医疗建议。

---

# 9. 到点提醒流程

状态机：

```text
WAITING
↓
FIRST_REMINDER
↓
父母确认完成 → DONE

或者

FIRST_REMINDER
↓
没有确认
↓
SECOND_REMINDER
↓
仍然没有确认
↓
ESCALATED
↓
通知子女
```

---

## 9.1 第一次提醒

示例：

> 到吃药时间了。已经吃过了吗？

操作：

```text
吃过了
稍后提醒
```

语音也必须支持相同操作。

---

## 9.2 第二次提醒

例如 30 分钟后再次提醒：

> 刚才的吃药提醒还没有确认。已经吃过了吗？

---

## 9.3 通知子女

达到配置阈值后：

通知子女。

但信息必须描述为：

> “今天 9:00 的提醒经过两次提醒后仍未确认。”

禁止描述为：

> “妈妈没有吃药。”

因为系统只能知道“没有收到确认”。

原型对此已有明确边界：持续未确认只代表没有回应，不代表没有完成，也不能输出医疗结论。fileciteturn1file15L848-L861

---

# 10. F03 关怀理解

这是 Coco 最重要的 AI 能力之一。

## 10.1 示例场景

用户：

> 今天腿有点酸。

AI第一反应不是调用工具，也不是通知子女。

先进行陪伴：

> “腿有点酸呀，听起来不太舒服。是今天才开始的吗？”

用户：

> 昨天走得有点多，今天才酸，现在还能走。

AI可以继续有限追问。

---

# 11. 关怀对话原则

AI目标不是诊断。

AI负责：

```text
理解
安慰
澄清
整理
询问是否需要帮助
```

禁止：

```text
诊断疾病
给出药物建议
夸大风险
自动通知子女
```

---

# 12. 分享给子女

只有两种情况下允许分享。

### 情况A：父母主动要求

例如：

> 跟小林说一下。

### 情况B：AI提出建议，父母明确同意

例如：

AI：

> “要不要让小林有空的时候知道一下？”

父母：

> “好。”

---

# 13. AI生成家庭摘要

AI将长对话转成简短 Family Care Summary。

例如：

原始表达：

> 昨天下楼走得有点多，今天腿酸，现在还能正常走，也没有别的不舒服。

生成：

> 今天腿有些酸，目前能够正常走。你有空时问候一下就好。

父母发送前必须看到或听到最终内容。

原型同样要求家庭摘要默认不分享，只有父母选择告诉家人才进入发送流程。fileciteturn2file5L285-L297

---

# 14. CareSummary 数据模型

```json
{
  "id": "care_xxx",
  "parent_id": "user_parent",
  "child_id": "user_child",
  "summary": "今天腿有些酸，目前能够正常走。",
  "urgency": "LOW",
  "reply_expectation": "WHEN_AVAILABLE",
  "source": "PARENT_CONVERSATION",
  "parent_confirmed": true,
  "created_at": ""
}
```

urgency MVP只允许：

```text
LOW
ATTENTION
```

不设计复杂医学风险等级。

---

# 15. F04 子女今日首页

子女打开 App 后首页优先回答三个问题。

```text
父母今天整体怎么样？
有没有需要我关注的事情？
我要不要联系父母？
```

---

## 15.1 页面结构

顶部：

> 今天总体正常

例如：

> 已完成 1 项提醒，没有明确异常。

第二部分：

### 需要关注

例如：

> 家人今天腿有些酸，希望你有空问问。

第三部分：

### 提醒状态

例如：

> 今天有 1 项提醒暂未确认。

---

# 16. 首页状态规则

状态只设计三个等级。

```text
NORMAL
ATTENTION
NEED_CONTACT
```

### NORMAL

没有需要子女处理的事情。

### ATTENTION

有父母主动分享的信息。

例如：

> “腿有些酸，希望你有空问问。”

### NEED_CONTACT

连续提醒没有收到确认。

例如：

> “9:00提醒经过两次提示仍没有收到确认，建议电话联系。”

禁止：

> “父母可能发生危险。”

系统没有依据时不能推断。

---

# 17. F05 子女报平安

目的不是完整聊天。

而是降低子女主动联系父母的成本。

---

## 17.1 快捷状态

子女可以一键选择：

```text
吃过饭了
正在忙，一切都好
已经到家
准备休息
```

---

## 17.2 自定义语音

子女也可以说：

> “刚吃过饭，马上开会，晚上忙完再联系。”

AI转换为老人更容易理解的表达：

> “小林已经吃过饭了，现在准备开会，一切都好，晚上忙完再联系。”

发送前子女必须预览。

这是原型已有的“AI转译预览 → 确认发送”逻辑。fileciteturn2file12L640-L665

---

# 18. 父母接收报平安

父母收到后，可可直接用自然语言转述：

> “小林已经吃过午饭。她现在工作有点忙，不过一切都好。”

父母可以：

```text
知道了
简单回应
```

例如：

> “知道了，别太累。”

本次互动立即结束。

不制造：

> “正在等待小林回复”

之类状态。

---

# 19. F06 AI基础记忆

长期陪伴必须具备记忆能力。

父母端会保存每次语音通话的最终转写文本与工具调用记录，供本人在「历史记录」中回看。  
通话结束后，服务端用文本模型根据本次对话生成短标题，便于列表辨认；生成失败时用预览文案兜底。  
不存原始音频；默认不同步给子女；向家人同步仍须经父母明确确认（关怀摘要等）。

长期记忆（`memories`）保存有长期价值的信息。语音陪伴中读写对用户无感：接通时注入已有记忆，对话中静默写入；不在通话历史里展示记忆工具摘要。父母仍可在「可可记得的我」查看与删除。提醒创建、确认提醒、分享给家人仍须父母明确确认。

例如：

```text
喜欢晚饭后散步
女儿叫小林
通常晚上十点睡觉
喜欢听老歌
女儿工作日上午比较忙
```

---

# 20. Memory 数据模型

```json
{
  "id": "memory_xxx",
  "user_id": "user_xxx",
  "content": "喜欢晚饭后散步",
  "category": "PREFERENCE",
  "source": "VOICE",
  "confirmed": true,
  "created_at": "",
  "updated_at": ""
}
```

category MVP支持：

```text
PROFILE
FAMILY
PREFERENCE
ROUTINE
```

---

# 21. 记忆写入规则

聊天过程中 AI 判断到可能值得记忆的信息。

例如用户说：

> 我一直喜欢晚饭后出去走一走。

语音侧静默调用 `save_memory` 落库，不问「要记住吗？」，也不口头说「我帮你记住了」。  
已有近似内容时不重复保存。通话历史不展示记忆工具行；运营与父母通过记忆列表查看。

---

# 22. 用户控制记忆

父母必须可以查看：

> 可可记得的我

首版只支持两个操作：

```text
查看
删除
```

暂时不做复杂的逐字段编辑系统。

如果内容错误：

删除后重新通过聊天建立即可。

原型本身也强调记忆需要可见、可删除。完整对话原文仅父母本人可查，不默认同步子女。fileciteturn1file0L11-L29

---

# 23. 家庭关系模型

MVP只支持：

```text
1名父母
+
1名主要子女
```

避免首版进入复杂家庭成员权限设计。

```json
{
  "family_id": "family_xxx",
  "parent_user_id": "parent_xxx",
  "child_user_id": "child_xxx",
  "status": "ACTIVE"
}
```

后续版本再支持：

```text
夫妻老人
多个子女
兄弟姐妹
主要联系人
紧急联系人
```

---

# 24. AI统一输出协议

为了方便客户端开发，建议大模型不要直接控制页面。

大模型统一返回结构化结果。

```json
{
  "reply": "好，我会每天晚上八点提醒你。",
  "intent": "CREATE_REMINDER",
  "action": {
    "type": "CREATE_REMINDER",
    "payload": {}
  },
  "ui": {
    "type": "CONFIRMATION"
  },
  "memory_candidate": null
}
```

客户端根据：

```text
intent
action
ui
```

决定调用业务 API 和展示页面。

---

# 25. AI严禁直接执行的操作

以下操作必须经过业务服务层。

```text
创建提醒
修改提醒
删除提醒
通知家人
保存长期记忆
删除记忆
```

正确流程：

```text
用户
↓
LLM理解
↓
生成Action
↓
业务代码验证
↓
用户确认
↓
业务API执行
↓
返回结果
↓
LLM自然语言反馈
```

LLM不能自己声称：

> “已经设置好了。”

除非业务 API 确认成功。

# 28. 通知类型

MVP只保留三类通知。

```text
REMINDER
CARE_MESSAGE
CHILD_STATUS
```

其中：

REMINDER  
父母自己的提醒。

CARE_MESSAGE  
父母主动授权分享给子女的信息。

CHILD_STATUS  
子女发给父母的报平安消息。

# 29. MVP删除 / 延后功能

以下功能不进入第一版。

## 29.1 删除「帮我看看」

包括：

- 系统分享短信；
- iOS Share Extension；
- Android Share Target；
- 图片 OCR；
- 看包装日期；
- 摄像头识别。

原型已经设计了这一完整生活助手流程。fileciteturn2file8L429-L455

但这一功能和“家庭陪伴”核心闭环关系较弱，同时涉及系统分享、多模态识别、权限和不同平台适配。

建议放到 V1.5。

---

## 29.2 删除独立「今天」任务中心

原型中设计了完整事项队列以及“继续下一项”的逻辑。fileciteturn2file2L127-L139

MVP不需要专门设计复杂任务中心。

待办直接通过：

```text
首页
AI主动提醒
消息卡片
```

完成即可。

用户量和任务类型增加后再增加“今天”。

---

## 29.3 延后「子女远程建议提醒」

原型允许子女提出提醒建议，由父母确认后生效。

产品逻辑合理，但第一版会增加：

```text
建议状态
发送
等待确认
拒绝
修改
双方同步
权限
```

等大量业务状态。

MVP先只允许父母自己创建提醒。

后续再加入“子女建议”。

---

## 29.4 删除复杂记忆管理

MVP只提供：

```text
查看记忆
删除记忆
```

暂不提供：

```text
编辑用途
设置分享范围
设置来源
逐字段修改
```

底层仍然可以保存 source 等信息，只是不暴露复杂 UI。

---

## 29.5 不接入 Apple Health / 健康平台

MVP不接入：

```text
Apple HealthKit
Android Health Connect
智能手表
血压设备
血糖设备
运动数据
睡眠数据
```

先验证陪伴和提醒闭环。

---

## 29.6 不做医疗Agent

可可不是医生。

MVP不做：

```text
疾病诊断
药物建议
症状判断
治疗方案
健康评分
```

只做：

```text
倾听
整理
提醒
连接家人
```

## 29.7 不做紧急救援

# 32. MVP核心产品原则

开发过程中如果出现需求冲突，按照以下优先级判断：

```text
1. 老人是否容易使用
2. 老人是否拥有控制权
3. 是否促进真实家庭联系
4. AI是否准确理解
5. 是否降低子女负担
6. 功能是否丰富
```

因此：

**宁愿少做功能，也不要让老人学习复杂操作。**

**宁愿 AI 多问一句，也不要错误执行。**

**宁愿不分享，也不要未经父母同意同步私人聊天。**

**可可的目标不是替代子女，而是帮助父母和子女更容易保持联系。**
